# notely-backend
# Notely — Backend (Flask)

REST API backend for **Notely**, a note-taking app. Pairs with the React frontend at
[calebfinney45-cloud/Notely](https://github.com/calebfinney45-cloud/Notely) via the
`VITE_API_URL` environment variable on the frontend side.

This backend handles user authentication, note CRUD, and profile management —
everything the frontend expects but doesn't implement itself.

---

## Why this stack

| Piece | Why |
|---|---|
| **Flask** | Lightweight, unopinionated — good fit for a small REST API without pulling in a full framework's worth of unused features. |
| **Flask-SQLAlchemy** | ORM layer over SQL, so models are Python classes instead of raw queries, and relationships (user → notes) are declarative. |
| **Flask-Migrate** | Wraps Alembic to track schema changes as versioned migration files instead of relying on `db.create_all()`, which can't handle schema changes safely once there's real data. |
| **Flask-Marshmallow** | Serializes SQLAlchemy models to JSON and validates incoming JSON before it touches the database. Also lets us explicitly exclude fields (like `password_hash`) from ever being serialized out. |
| **Flask-Bcrypt** | One-way hashing for passwords. Plaintext passwords are never stored or logged. |
| **Flask-JWT-Extended** | Issues signed tokens on login/signup. Chosen over server-side sessions because the frontend is a separate SPA on its own origin — a stateless token is simpler than managing cross-origin cookies. |
| **Flask-CORS** | The frontend and backend run on different ports/domains. Without this, browsers block the requests by default (CORS policy). |
| **python-dotenv** | Keeps secrets (DB URL, JWT secret) out of source control. |
| **gunicorn** | Production WSGI server — Flask's built-in dev server isn't meant to run in production (used on Render). |

## Project structure

```
notely-backend/
├── app/
│   ├── __init__.py        # app factory — creates and configures the Flask app
│   ├── config.py          # reads environment variables into config classes
│   ├── extensions.py       # single source of truth for db, migrate, jwt, bcrypt, ma, cors
│   ├── models/
│   │   ├── user.py         # User model, one-to-many with Note
│   │   └── note.py         # Note model, belongs to a User
│   ├── schemas/
│   │   ├── user_schema.py  # serialization/validation for User
│   │   └── note_schema.py  # serialization/validation for Note
│   └── routes/
│       ├── auth.py         # /auth — signup, login, me
│       ├── notes.py        # /notes — CRUD, scoped to the logged-in user
│       └── users.py        # /users — profile update, account deletion
├── migrations/              # generated by `flask db init`, tracks schema history
├── seed.py                  # populates demo data for local development
├── run.py                   # entry point
├── requirements.txt
├── .env.example
└── .gitignore
```

**Why a factory pattern (`create_app()`) instead of a single global `app`?**
It keeps extensions decoupled from a specific app instance, which matters for testing
(you can spin up a fresh app per test) and avoids circular imports between `models` and
the app object.

## Setup

### 1. Clone and create a virtual environment
```bash
git clone <this-repo-url>
cd notely-backend

python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
```

### 2. Install dependencies
```bash
pip install -r requirements.txt
```

### 3. Configure environment variables
```bash
cp .env.example .env
```
Fill in:
```
SECRET_KEY=some-random-string
JWT_SECRET_KEY=another-random-string
DATABASE_URL=sqlite:///notely.db      # or a Postgres URL in production
```

### 4. Set up the database
```bash
flask db init
flask db migrate -m "initial tables"
flask db upgrade
```
This creates the `migrations/` folder and applies the schema. Every future model
change should go through `flask db migrate` + `flask db upgrade` rather than editing
the database directly — that way the schema history is versioned alongside the code.

### 5. (Optional) Seed demo data
```bash
python seed.py
```
Creates a demo user (`demo@notely.com` / `password123`) with two sample notes, useful
for testing the frontend without manually signing up each time.

### 6. Run the server
```bash
python run.py
```
API is now available at `http://localhost:5000`.

### 7. Point the frontend at it
In the `Notely` frontend repo, set in `.env`:
```
VITE_API_URL=http://localhost:5000
```

## API reference

| Method | Endpoint | Auth required | Description |
|---|---|---|---|
| POST | `/auth/signup` | No | Create an account, returns a JWT |
| POST | `/auth/login` | No | Log in, returns a JWT |
| GET | `/auth/me` | Yes | Get the current logged-in user |
| GET | `/notes?page=1&per_page=10` | Yes | List the current user's notes, paginated |
| POST | `/notes` | Yes | Create a note |
| PUT | `/notes/<id>` | Yes | Update a note (must belong to the user) |
| DELETE | `/notes/<id>` | Yes | Delete a note (must belong to the user) |
| PATCH | `/users/me` | Yes | Update profile (name, picture) |
| DELETE | `/users/me` | Yes | Delete the account and all its notes |

Authenticated requests need:
```
Authorization: Bearer <token>
```

## Deployment (Render)

1. Create a **Postgres** instance on Render and a **Web Service** pointing at this repo.
2. Start command: `gunicorn run:app`
3. Set the same environment variables as `.env`, plus `DATABASE_URL` from the Render Postgres instance.
4. Render's Postgres URL starts with `postgres://`, but SQLAlchemy 1.4+ requires `postgresql://`.
   `config.py` patches this automatically at connection time.
5. Update `CORS` origins in `app/__init__.py` to the deployed frontend's URL instead of `*`.
6. Update the frontend's `VITE_API_URL` to the deployed backend URL and redeploy the frontend.

## Notes on scope

- Profile pictures are stored as a URL string, not an uploaded file — keeps the MVP
  simple. Swapping in real file uploads (e.g. to S3/Cloudinary) is a drop-in change to
  the `users.py` route later.
- "Logout" is handled client-side (discard the token) since JWTs are stateless by
  default. Server-side token revocation is a possible future addition but isn't
  required for this app's scope.
